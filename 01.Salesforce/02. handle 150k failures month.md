* No, ```tf-triage\build_index.py``` will not correctly handle 150,000 failures per month.

### ```tf-triage\build_index.py``` can handle
    * your pipeline is:
        - load all failures into memory
        - embed all failures at once
        - normalize all vectors
        - add them to a FAISS IndexFlatIP (exact search)
    * This works for:
        - small datasets (< 100k records)
        - demo workloads
        - local experiments

### ❌ What happens at 150k failures/month (1.8 million/year)
1. RAM Explosion
    * Embeddings are ~1536 dims (OpenAI-like).  
    * RAM needed: ```1536 dims × 4 bytes × 1,800,000 rows ≈ 11 GB```
    * Plus Python overhead → 15–18 GB total just to build index.
    * This exceeds typical dev machine or CI/CD runner memory.

2. Embedding cost + time explodes
    * Even if you self-host embeddings: ```150,000 failures × 12 months = 1.8M embeddings/year```
    * Embedding them all at build-time takes hours.

3. FAISS Flat index slow for millions
    * IndexFlatIP has O(n) query time: ```1.8M comparisons for every search```
    * This gives:
        - 50–150 ms per query → OK
        - But 20–100 queries/sec → slow
        - High CPU burn

4. ❌ Index rebuilds become impossible
    * Your current script rebuilds FAISS from scratch: ```delete old index → read all failures → re-embed → build index → save```
    * With millions of embeddings, this takes hours and is not realistic.

### 🚀 To handle 150,000 failures per month you need:
1. Switch from exact search to HNSW (Hierarchical Navigable Small World)
    * FAISS supports:

    |Index Type	|Use Case
    |-|-
    |IndexFlatIP	|small datasets (<100k)
    |HNSW (IndexHNSWFlat)	|1M–10M records
    |IVF-HNSW	|10M–100M+
    |PQ / OPQ	|compression for memory savings

    * For you, the best choice: ```faiss.IndexHNSWFlat(d, M=32)```
        - Fast, scalable, approximate, still very accurate.
        - This reduces query time from 150ms → 5ms on millions of vectors.

2. Make FAISS index incremental
    * Right now your index is “rebuild-only”.
    * We need to switch to append-only indexing:
        - New failures → embed → normalize → add to FAISS → save updated index.
    * This avoids the need to rebuild everything every month.

3. Use Postgres to store metadata, not all data in memory
    * You already said you want SQLite → Postgres.
    * Correct flow should be:
        - Postgres: 
            * failure_id
            * error_log
            * resolution
            * embedding (optional)
        - FAISS index: 
            * only stores vectors (1536 dims)
            * stores mapping: faiss_index_id → failure_id

4. Build index in mini-batches, not in one giant load
    * Example: ```batch_size = 5,000```
    * The build process becomes:
        ```
        while rows in postgres:
            embed_batch()
            normalize()
            index.add(batch)
            save intermediate index
        ```
    * This allows:
        - low memory use
        - resumable builds
        - incremental updates

5. Schedule monthly compaction / refresh
    * Instead of raw rebuilds:
        - daily incremental updates
        - monthly HNSW rebuild for accuracy optimization
